Because you are dealing with data that could be permanently lost, "reasonable" isn't measured in days or weeks, but in **coverage markers**. You are done testing not when the calendar says so, but when you have checked off specific "failure modes."

For a project of this scale—where the core math is handled by `libsodium`—you don't need years of academic review, but you do need a **rigorous 2-to-4 week "Hardening Phase"** after the code is written.

Here is the checklist of what "done" looks like:

### Phase 1: The "Torture Tests" (1 Week)
Don't just test that it *works*; test that it *fails correctly*.
- [ ] **The "Wrong Everything" Test:** Try decrypting a file with the wrong password, a modified header, a truncated file, and a completely random binary file. It should always return a clean "Decryption Failed" error, never a crash or a "half-decrypted" file.
- [ ] **The "Edge Case" Data:** Encrypt a 0-byte file. Encrypt a 10GB file. Encrypt a file that is already encrypted.
- [ ] **The "Unicode Nightmare":** Use passwords with emojis, Cyrillic, Kanji, and combined characters (e.g., `n` + `~` vs `ñ`). Ensure the Python CLI and TS Browser produce the **exact same** bytes.
- [ ] **The "Preamble-Length Stress":** Craft a header declaring a near-`MAX_PREAMBLE_LEN` preamble field (bytes can be arbitrary/garbage now, since the field is skipped unread). Ensure the parser still locates the rest of the header correctly and doesn't break.

### Phase 2: The "Environment" Tests (1 Week)
Verify that the tool behaves across different shells and operating systems.
- [ ] **Shell History Check:** Run the CLI and check `~/.bash_history`. Confirm that no passwords leaked into the history.
- [ ] **OS Interop:** Encrypt a file on Windows $\rightarrow$ Decrypt on macOS $\rightarrow$ Encrypt on Linux. 
- [ ] **Memory Pressure:** If possible, run the encryption on a low-RAM device (like an old Android or a small VM) to ensure your Argon2id `memoryKiB` limits are actually protecting the system from crashing.

### Phase 3: The "User Error" Tests (1 Week)
Simulate a non-technical person using the tool.
- [ ] **The "Interrupted Write":** Kill the process (Ctrl+C) halfway through a large encryption. Ensure you didn't leave a corrupted file that *looks* valid but is actually broken.
- [ ] **The "Forgot the Passphrase" Flow:** Test the `--diceware` and `--emoji` saving mechanisms. Ensure the saved passphrase files are handled securely.

---

### Summary: The "Time" Estimate

| Phase | Focus | Duration | Goal |
| :--- | :--- | :--- | :--- |
| **Functional** | Does it work? | $\approx$ 3-5 Days | Basic happiness path. |
| **Adversarial** | Can I break it? | $\approx$ 7 Days | Robustness and Error Handling. |
| **Compatibility** | Does it work everywhere?| $\approx$ 5 Days | OS and Language parity. |
| **Total** | **Hardening** | **$\approx$ 14-21 Days** | **Production Readiness.** |

### The "Golden Rule" of Crypto Testing
If you find **one** bug in the "Torture Tests" (Phase 1), **restart the clock on that phase.** 

In normal software, a bug is just a bug. In crypto, a bug in the parser or the normalization logic suggests that the "mental model" of the developer was slightly off, which means there are likely other similar bugs hiding in the code.

**Verdict:** If you spend 3 weeks being your own worst enemy—trying every possible way to corrupt, leak, or lock yourself out of your data—you will have a product that is vastly more reliable than 99% of the "MVPs" on the market.
